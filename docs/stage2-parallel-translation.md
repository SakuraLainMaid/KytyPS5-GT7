# Stage 2：GPU 线程的并行翻译（设计草案）

## 现状（1440p GT7 比赛，20 秒 Tracy，2026-10-25，stage2 @ f53b1f7）

- 约 5 fps。GPU 线程 67% 的时间在忙，约 13.5 秒 / 20 秒。
- 20 秒里有 44 万次绘制、7 万次 dispatch，平均每次绘制约 25 µs。
- 时间分散在约 30 个函数里，最大的一个也不到 GPU 线程时间的 11%：

| 函数 | 自身时间 | 次数 | 性质 |
|---|---|---|---|
| DrawIndex（未细分的部分） | 2.23 s | 37 万 | 混合 |
| PrepareBindings | 1.48 s | 95 万 | 混合：查缓存 + 打包绑定 |
| CpOpReleaseMem | 0.86 s | 3.6 万 | 按顺序，碰内存 |
| DrawPrep::Validate | 0.86 s | 89 万 | 校验预处理结果 |
| RebindImages / RebindBuffers | 0.98 s | 95 万 | 查缓存 |
| CommitBindings | 0.52 s | 51 万 | 纯主机侧 |
| SRT refresh（三处） | 0.85 s | | 部分已由预处理代做 |
| Sync::Tracker / SynchronizeBuffer | 0.59 s | 325 万 | 碰共享缓存 |
| ResolveRender{Color,Depth}Target | 0.56 s | 145 万 | 碰贴图缓存 |
| ShaderGetStatic* / ApplyAttribSemantics | 0.53 s | 160 万 | 只读、可缓存 |
| ProgramCache::Get / CreatePipeline | 0.49 s | 133 万 | 查表 |

## 已经并行的部分

- **Vulkan 录制**：独立的录制线程（`KYTY_RECORD_THREAD`），GPU 线程只把命令和参数排进队列。
- **描述符遍历**：绘制预处理扫描线程（`DrawPrepScanner`，2 个工作线程）提前走 SRT，GPU 线程只校验并取用结果（`DrawPrep::Validate`）。
- **管线编译**：8 个后台线程。

## 约束

1. **全局锁**：`RenderExecutor` 的每次绘制都在 `RendererLock` 之下，整个渲染器默认单线程。
2. **共享缓存会被改动**：缓冲区缓存、贴图缓存、内存跟踪、BDA 页表、GPU 写入标记（`MarkWritten`）。它们的语义依赖程序顺序：前一个绘制写了什么，后一个绘制读到的就得是它。
3. **命令顺序**：命令缓冲里的顺序就是游戏提交的顺序，不能乱。

## 可选方案

### A. 两段流水线（推荐的主线）

- **第一段（GPU 线程）**：保留所有必须按顺序、会改共享缓存的工作，包括同步缓冲区、贴图和渲染目标查找、写入标记、页表，然后把结果打包成一份"绘制描述"。
- **第二段**：拿到"绘制描述"后，做纯主机侧的部分：绑定数据打包、描述符堆写入（`CommitBindings`）、管线查找、动态状态、Vulkan 命令。
- 第二段可以直接放进现有的录制线程：它本来就在按顺序执行 GPU 线程排进来的闭包。这样不用新建线程，顺序也自然保证。
- **上限**：如果纯主机侧约占 40–45%，GPU 线程最多能快约 1.7–1.8 倍。
- **难点**：`PrepareBindings` 和 `DrawIndex` 自身里两种工作交织在一起，要拆函数。

### B. 扩大绘制预处理

- 让扫描线程多做些只读工作，例如 `ShaderGetStatic*`、管线键计算、`ProgramCache::Get` 的查找，GPU 线程照现在的方式校验后取用。
- 框架现成，风险低；但校验本身也要花时间（Validate 现在就占 0.86 s），收益有天花板。

### C. 相同绘制去重（单线程）

- 连续的绘制常常用同一条管线、同一套绑定。缓存上一次的绑定结果，输入完全相同就跳过 `PrepareBindings`、`Rebind*` 和 `CommitBindings`。
- 不是并行，但风险低、见效快。收益取决于重复率，要先量。

### D. 多个工作线程同时翻译不同绘制

- 需要把缓冲区和贴图缓存改成可并发访问的结构，还要处理绘制之间的写后读依赖。
- 工作量以月计，不建议现在做。

## 建议路线

0. **测量**（约 1 天）
   - 在 Tracy 里把每次绘制的时间分成"碰共享缓存"和"纯主机侧"两类，确认方案 A 的上限。
   - 统计相邻绘制的绑定输入（程序、用户数据、SRT 内容）完全相同的比例，判断方案 C 值不值得。
1. **方案 C**（若重复率高，约 2–3 天）：单线程去重。用开关控制，可以 A/B 对比；必要时加校验模式，逐次和完整计算的结果比对。
2. **方案 A，第一步**（约 1 周）：先把最干净的纯主机侧工作，即 `CommitBindings`、动态状态和管线查找，挪进录制线程的闭包；用 Tracy 确认 GPU 线程变短、录制线程没被压满。
3. **方案 A，第二步**（约 1–2 周）：拆开 `PrepareBindings`，把打包部分也挪过去。
4. **方案 B**：视前几步之后的剩余情况而定。

每一步都单独提交，有环境变量开关，用同一场比赛的 Tracy 对比。

## 预期

- GPU 线程的时间省下 20–40%。
- 帧率不一定同比例上涨：游戏线程等回读（20 秒里累计约 36 秒）和显存超预算这两个瓶颈还在。每一步都要重新测量，看瓶颈移到了哪里。
